# Decisions

One line each: date, decision, why. Reviewed in batches.

- 2026-09-04 — Size budget is measured on Cortex-M4/Thumb-2 (nRF52) at `-Os`, engine-only `.text`+`.rodata`; ESP32 (Xtensa, RISC-V) is secondary with measured multipliers 1.12x / 1.37x. — Boogie named nRF52/ESP32 as targets; Thumb-2 has the toolchain on hand.
- 2026-09-04 — Speed is not a requirement; backtracking with a step budget is acceptable. — Boogie: short strings only.
- 2026-09-04 — UTF-8 code-point matching is in v1; accent-aware case folding is not. — Superseded by the compiler-expanded Unicode `i` decision below.
- 2026-09-04 — `\b`/`\B` are in v1; the multiline `m` flag is v1.1 (its byte cost is measured in the spikes). — Boogie.
- 2026-09-04 — Test oracle is Python 3 `re` with `re.ASCII` (Perl/Python leftmost-first semantics, keep-last captures, one empty iteration allowed). — Default taken: a single flag gives exactly the v1 semantics and pcre2 agrees on 2079/2081 cases; JS differs on empty-iteration captures. Pending review.
- 2026-09-04 — License MIT. — Boogie: "MIT or similar".
- 2026-09-04 — GitHub repo created private; flip to public at the first release. — Boogie: "we can release it later"; one command to change.
- 2026-09-04 — README and code in English, internal studies in Hungarian. — Default for an open-source library.
- 2026-09-04 — Test corpus is language-agnostic (JSONL + CLI contract) so the runner can be C-only or JS-compiler + C-engine. — Boogie: that architecture choice is still open.
- 2026-09-04 — Repetition of a nullable atom (`(a*)*`, `(|a)+`, `()+`) is out of scope: the engine may reject it at compile time. — Boogie: no real use case. Removes the empty-iteration rule from v1 and lets the matcher drop its empty-loop protection; the corpus tags those 139+222 cases.
- 2026-09-04 — Architecture is a separate JavaScript compiler plus C matcher VM. — Keeps Unicode folding and parsing out of the embedded binary.
- 2026-09-04 — Matcher VM has a hard 600-byte Cortex-M4 ceiling; compiled pattern bytecode is measured separately. — Boogie: the goal is the world's smallest regexp implementation.
- 2026-09-04 — The `i` flag uses compiler-expanded Unicode simple case folding; multi-code-point folds such as `ß` → `ss` remain out of scope. — The feature adds pattern bytes but no VM instructions.
- 2026-09-04 — Backtracking uses caller-provided explicit workspace, not C recursion. — Keeps task-stack use constant on nRF52/Mynewt and reports workspace exhaustion separately as `RE_SPACE`.
- 2026-09-04 — Nullable-repeat corpus labels come from an independent structural analyzer. — Compiler over-rejection must fail differential testing instead of converting itself into an allowed skip.
- 2026-09-05 — Keep the 546-byte precompiled-pattern VM as product A; investigate the measured 2796-byte no-`i` embedded C compiler as optional product B-lite. — Runtime pattern compilation has value, but full Unicode `i` requires roughly 3.6–4.9 KB of fold data alone.
- 2026-09-05 — Product B (runtime-supplied patterns) is a direct pattern interpreter with no compile step, not an on-target C compiler. — Measured apples-to-apples: 1849 B versus 2796 B for compiler+VM, 34% smaller with more features. The compact bytecode's *encoder* is ~570 B of the C compiler; a direct interpreter never builds it. Compact bytecode pays for itself only when the compiler stays off-device.
- 2026-09-05 — Product B must bound C-stack use before it ships. — It currently recurses 104 B per quantified-group iteration, so `(a|b)*` overflows a 4 KB nRF52 task stack at 34 characters, and `(a*){65536}` segfaults; the step budget does not catch either. Same fix as product A: caller-provided workspace.
- 2026-09-05 — Host Unicode behaviour enters product B through two callbacks, `other_case(cp)` and `is_word(cp)`, not through built-in tables. — An embedding scripting language already has these; duplicating them would cost 3.6–4.9 KB. A single `other_case` is the right primitive for both literals and class ranges; NULL falls back to ASCII. Costs +40 B compiled out, +134 B enabled.
- 2026-09-05 — Product B size target is 1400 B including the hook layer; feature removal is not an acceptable way to reach it. — Combinations such as `NO_CLASSES`+`NO_BOUNDED` (1376 B) are profiles, not the all-in engine. Boogie set the target against the full feature set.
- 2026-09-05 — Parallel size-optimisation agents must get disjoint territory, or run as a relay. — Eight parallel agents on one baseline promised 892 B and delivered 307 B: six independently found the same three function merges. Recorded so the next round is not repeated the same way.
- 2026-09-05 — Two engines are maintained, deliberately: product A (separate compile step, JavaScript compiler plus compact-bytecode VM) and product B (all-in, compiles on-target or not at all). — Boogie's product decision. It frees B to pick whatever internal format minimises compiler+matcher combined, with no obligation to match A's bytecode, and it protects A's 546-byte figure, which exists only because its format is compact.
- 2026-09-05 — Product B's remaining size work targets the format axis (dumber format, smarter matcher), not further micro-optimisation of the direct interpreter. — Eight parallel and three relay agents took the direct interpreter from 1941 to 1634 B; the measured feature ledger shows the rest is feature cost, not slack. Boogie: "ehhez egy új engine logika kellene".
- 2026-09-05 — Product B's size target is revised from 1400 to approximately 1550 bytes including the host hook layer. — Boogie accepted the measured evidence: the format axis is closed (see below), the remaining reserve is roughly 200 B of core compression, and 1400 would require giving up a v1 feature. At ~1550 it is still the smallest measured engine with this feature set.
- 2026-09-05 — The compiler/format axis for product B is closed: no compile step. — Measured, not estimated. Pure re-scanning in the direct interpreter is only 62 B; every other apparent saving moves into the compiler. Combined sizes: 1634 (no compiler) < 1784 (intermediate format) < 1896 (fully resolved) < 2796 (compact bytecode). The curve rises monotonically from the zero-compiler endpoint, so no intermediate format wins. Encoding a quantifier as a record is 12 B *more* than testing the syntax character.
- 2026-09-05 — OPEN: on Cortex-M0+ the product A VM pulls `__gnu_thumb1_case_uqi` from libgcc, so "no libc dependency" is true on Cortex-M4 but not on Thumb-1 as built. — Found by the bytecode-backend research, which measures linked flash rather than object `.text`. Thumb-1 emits a switch jump table for the opcode dispatch. Two measured options: accept the helper and report the honest linked size (560 B rather than the object's 538 B), or build Cortex-M0+ with `-fno-jump-tables` for a clean 586 B. CI now fails on Cortex-M4 undefined symbols and warns on Cortex-M0+ until this is decided. Product B is unaffected: its dispatch is an if-chain, and it is clean on both targets.
- 2026-09-05 — Size measurement should report linked flash, not only object `.text`. — Object size hides helpers the linker pulls in; that is exactly how the Thumb-1 libgcc dependency stayed invisible. `tools/measure.sh` now lists undefined symbols for both ARM targets.
- 2026-09-05 — Tail sharing is on by default in the JavaScript compiler. — Free: 8.37% smaller pattern bytecode measured over 3587 distinct corpus programs, with the VM byte-for-byte unchanged at 546 B and zero semantic difference across 7197 differential cases. The pass keeps its output only when it is actually shorter and discards a candidate whose relocation no longer fits a 16-bit offset, so it can neither enlarge a program nor emit an invalid one. `{tail: false}` emits the unshared program and CI runs both corpora in both modes.
- 2026-09-05 — OPEN: the CHAR plus escaped-branch format (584 B VM, 27.71% smaller bytecode) is measured but not adopted. — It buys 72380 B of aggregate bytecode saving for 38 B of VM, breaking even at two distinct patterns on corpus average, but the encoding is incompatible with the current operands, so compiler and VM must ship together. Worth taking when an application's pattern set is large enough; the decision belongs with a release, not with a measurement.
- 2026-09-05 — The product A bytecode format is FROZEN as v1 at commit 5365616 (tail sharing on, 546 B VM). — MagiScript is the first consumer, and it ships the two halves separately: the JavaScript compiler goes out in the editor, the VM in device firmware, and a pattern compiled today has to match on a device flashed months earlier. That makes the format a contract exactly like MagiScript's own bytecode format, not an implementation detail. The measured CHAR-plus-escaped-branch variant (584 B VM, 27.7% smaller patterns) is deferred to a v2, which would need its own engine capability id so a compiler can tell the two VMs apart.
- 2026-09-05 — MagiScript consumes product A only; product B stays a spike. — MagiScript's patterns are written in the program, so they are compiled off-device in the editor and only matched on the device; there is no runtime `RegExp(text)`, which is the one thing B exists for. A stays 546 B because nothing on the device ever parses a pattern.
- 2026-09-05 — OPEN: `compileRe` silently MISREADS JavaScript syntax it does not implement instead of rejecting it — `(?=a)` becomes a group matching the literal `?=a`, `\1` matches the digit `1`, `é` matches `u00e9`, `[\n]` matches the letter `n` (`classAtom` ignores control escapes). Found by the MagiScript integration, which now pre-scans a pattern and refuses lookaround, named groups, backreferences and `\u \x \c \p \k \0 \A \z \Z` before calling the compiler, and rewrites control escapes inside a class to the character. — The library should refuse these itself (an unknown escape or construct is an error, never a literal), so that every embedder gets the same answer; the pre-scan is a workaround, not the fix.
- 2026-09-05 — Product B is 1518 bytes and stays portable C; hand-written Thumb-2 assembly is not adopted. — Two rounds took it from 1712: an algorithmic relay to 1536, then 18 surviving bytes from a size-coding round. The assembly variant measured 46 bytes smaller with a C fallback, but by the time it existed the merged `atom()` was no longer the function it was written against, and it would make the product two-file, Thumb-2-only, never covered by sanitizers, and dependent on a qemu differential in CI.
- 2026-09-05 — Instruction-encoding work on product B is closed; further bytes must come from algorithm or structure. — The whole Thumb-2 instruction set is worth a net 32 bytes on this code (1.9%): the Thumb-1 build is 1744 against 1712, and four functions are *smaller* under the poorer ISA. Two independent rounds converged on ~80% the same transformations, so the coding-level seam is worked out.
- 2026-09-05 — The corpora do not cover malformed UTF-8; only differential fuzzing does. — A sentinel change that saved 8 bytes stayed green on both corpora while breaking 245 of 13 M fuzz cases, because an overlong `F0 80 80 80` decodes to code point 0, making 0 a real pattern member. Anyone touching the decoder or the sentinel values must run differential fuzzing, not just the corpus.
- 2026-09-05 — OPEN (v2): a greedy repeat leaves one choice point per consumed character, so the reachable input length is bounded by the caller's workspace depth (MagiScript: depth 16 → a groupless `\w+` matches 39 characters). Where the compiler can prove the repeated atom cannot overlap the continuation (`\w+` before a space or `$`, `\d+` before `-`, `.*` at the end), a POSSESSIVE repeat — consume as much as possible, push no choice point — would lift the bound entirely. That needs a new instruction, so it belongs to the v2 format with its own capability id; v1 stays frozen. — Found by the MagiScript integration; the immediate remedy there is a deeper workspace in static RAM.
